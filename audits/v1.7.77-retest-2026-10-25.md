## What changed

1. `POST /api/geofences` accepts `enabled`. The screen payload with alarm switches off is covered by `create-geofence.dto.spec.ts`.
2. Device failures store `fw_error` / `sw_error`. Rollout `statusReason` falls back to the device sentence. Migration `0057_ota_plain_reasons.sql` backfills old `FAILED` rows and missing halt / rollback / completed-with-failure reasons.
3. A complete `fw_*` set is not wiped by stale `sw_*` in the same push. Assigning firmware clears idle `sw_*`, and a finished update clears its own shared target when nothing of that type is still running.
4. A boot report fails only the latest UPDATED row (`failUpdatedById`). A queued target is left in place.
5. Cancel clears the shared target. A version that arrives with `fw_state` or `sw_state` is not stored as the running image.
6. A rollback child that halts or is cancelled moves the parent from ROLLING_BACK to HALTED with a reason. All children completed still ends as ROLLED_BACK.
7. The rollout form can keep named devices in the last wave. The rest of the fleet is still shuffled.
8. `examples/OtaHealthCheck_mqtt` defines `verifyRollbackLater()`.
9. The geofences guide says an empty fence field uses name order, A to Z.
10. Delete allows a stopped rehearsal whose package or device name starts with `QA ` or `QA-`. Production rows stay.
11. The rule engine header shows the geofence warning. Example: Block the next start connects `entered` to the inside log. The command stays on `outside` and `left`.
12. Halt confirm text is unchanged. See the note below.

### Follow-up bugs (local fix, not deployed)

1. After cancel, a later `fw_error` overwrote an older FAILED row’s plain reason. **Board re-test Pass** (25 Oct ~21:55). Platform only fills a placeholder on a matching package. SDK clears error after UPDATED and at download start.

2. After UPDATED 1.2.0, a failed 1.0.0 download published `fw_version=1.0.0` without treating it as package identity; the platform read that as a boot report and failed the good 1.2.0 row. **Board re-test Pass.** Platform ignores progress/failure package versions as boot reports; SDK `fail()` does not republish bare `fw_version`.

3. After a failed download the UI showed no `fw_version` because progress handling **deleted** the stored client version. **Local fix:** skip writing the download package version, but keep the last boot-reported value. Not board-retested for this third fix. Not deployed.
